Code Mode / Go

Anatomy of a Code Mode Request

A model writes a small program. The program runs in a sandbox. Every time it wants something real, it calls back to Go, and Go decides whether to allow it. Here is that trip, one step at a time.

The short version

If you read nothing else

Ordinary tool use makes the model do the work one call at a time. Ask it to finish fifty tasks and you get fifty round trips, with every intermediate result passing through the model.

Code mode flips that. The model writes a program instead of a call. The program loops, filters, and chains at machine speed inside a sandbox, and only the final answer comes back. The model is asked once.

The sandbox can't reach your database, your network, or your secrets. It gets exactly one function, and that function goes back to Go, which checks a registry before letting anything run.

Before any request: build time

Runs once, when contracts change

Two things happen long before a user types anything. They turn your service definitions into a catalogue the system can search and check against.

  1. B1

    Protobuf files describe your services

    You write proto/todo.proto as normal, with two extra annotations: a namespace on the service and a description on each method. The description is what a model will read later, so write it for a reader, not a compiler.

  2. B2

    The generator turns them into a registry

    make generate asks Buf for a descriptor set, then registry/main.go walks it and writes registry/registry.json. Each entry has a friendly name like todos.complete, the real rpc path todo.v1.TodoService/Complete, the description, and the input and output field types.

    Those field types come out as TypeScript — string, number[], Record<string, string> — because that is what the model will be shown.

The eight steps of a request

Runs every time someone asks for something

  1. 01

    A request arrives

    Someone says "add two todos and finish the first one." Go takes it from here. Nothing has been sent to a model yet.

  2. 02

    Search picks the relevant capabilities

    mode.Search ranks the registry against the request and returns the best few matches. With a database configured this is real semantic search — the request is embedded into a vector and compared by cosine distance. Without one, the demo falls back to counting keywords.

    Search runs on the host, before the model exists in the picture. That ordering is deliberate, and step 4 explains why.

  3. 03

    Matches become a prompt

    Each match is rendered as a TypeScript signature with its description above it. Add the house rules — write a function body, no async, no imports, return the answer — and that is the entire system prompt. 

    /** Marks a todo item as completed by ID. */
codemode.execute(name: "todos.complete", input: { id: number }): { todo: Todo };

    Field order is sorted, so the same match set always produces the same bytes and the prompt stays cacheable.

  4. 04

    The model writes a program

    The prompt and the request go to whichever provider is configured. Back comes a few lines of code. It is ordinary code — no magic, no framework: 

    const { todos } = codemode.execute("todos.list", {});
const pending = todos.filter(todo => !todo.completed);
const done = codemode.execute("todos.complete", { id: pending[0].id });
return "completed " + done.todo.title;

    That is JavaScript because the JavaScript engine is configured. The engine writes its own prompt, so with SANDBOX_ENGINE=lua the model is asked for Lua instead and the same job comes back as ipairs and ... Steps 1 through 3 and 6 through 8 do not change.

    Note what the model was told versus what it can run. Those are two different lists, and keeping them apart is the whole security story.

  1. 05

    The sandbox runs the program

    A fresh JavaScript interpreter is created for this one run. Its global scope contains exactly what Go put there and nothing else: no require, no fetch, no filesystem, no process. There is one object, codemode, with one method, execute.

    Two bounds are enforced from outside the program: a wall-clock timeout and a cap on how many capability calls it may make. A program that loops forever is interrupted; a program that tries a thousand calls is stopped at the budget.

  2. 06

    Each call crosses back into Go

    codemode.execute is not JavaScript. It is a Go function bound into the interpreter. When the program calls it, the interpreter blocks, Go takes over, and the program resumes only when Go returns a value.

    This is the only channel. Whatever the program computes, the only way it affects the outside world is by putting a name and some JSON through this one function.

  1. 07

    Go checks, resolves, and calls

    Three things happen in order, and the order matters. Check the name against the registry map — an unknown name is an error and the program never reaches the network. Resolve it to the real protobuf path. Call the trusted transport with that path and the JSON.

    Your application is untouched by any of this. It validates its own input, enforces its own permissions, and owns what "complete" actually means. Per-user authorization belongs here, in the transport, not in the prompt.

  2. 08

    The answer comes back

    The response is decoded and handed to the waiting program as a plain JavaScript object. The program keeps going — filtering it, looping over it, calling again. When it finally returns, that single value is the answer to the user.

    If the program throws, the error is fed back to the model along with the source that failed, and it gets another attempt. Three by default. Transport errors are not retried this way — only mistakes the model can actually fix.

Why bother with a sandbox at all

Go makes the call either way

A fair question: if Go performs the gRPC call regardless, what is the sandbox buying? The answer is not security — it is arithmetic.

Without a sandbox, every intermediate result travels back through the model's context. Fifty todos means fifty round trips, fifty times the tokens, fifty times the latency. With a sandbox, the loop runs at machine speed and the model is asked exactly once.

The isolation is the price of letting model-written code run at all. The round-trip collapse is the point.

Who enforces what

Where each guarantee actually lives

A useful habit when reasoning about this system: for any rule you care about, name the component that enforces it. If the answer is "the prompt", it is not enforced.

Guarantee Enforced by Not by
Only registered capabilities run The registry map in codemode.Execute The prompt
No filesystem, network, or modules The sandbox's empty global scope Instructions to the model
Programs terminate Timeout and call budget on the runner Well-behaved generated code
Input matches the schema Your application, at the RPC boundary The TypeScript in the prompt
This user may do this thing Your transport or a bridge in front of it Anything described here
Secrets stay secret They live host-side and never enter the sandbox The program choosing not to look
One honest caveat. The default sandbox is an in-process interpreter. It denies ambient capabilities and bounds time and calls, which is right for code your own host asked a model to write. It is not a defence against a determined attacker sharing your process. Before running programs authored for untrusted end users, swap in a runner backed by a separate process or a container — the bridge shape does not change, only the transport.

The three swappable parts

Chosen by environment, not by code

Three pieces of this pipeline are interfaces with more than one implementation, each selected by an environment variable. Nothing else in the system knows or cares which one is in play.

Environment reference

Variable Values Default
LLM_PROVIDER claude · openai whichever key is set
LLM_BASE_URL any compatible endpoint the vendor's
CAPABILITY_DB sqlite · postgres sqlite
CAPABILITY_DB_DSN file path or connection URL unset — keyword search
EMBEDDING_MODEL any embeddings model text-embedding-3-small
SANDBOX_ENGINE goja · starlark · lua goja
SANDBOX_TIMEOUT Go duration 30s
SANDBOX_MAX_CALLS integer 50

Run it

Two commands

With no keys and no database, everything still runs — search falls back to keywords and a fixed program stands in for the model, so you can watch the path without credentials. 

make demo-todo

# or, with a model actually writing the program:
export ANTHROPIC_API_KEY=...
go run ./examples/todo -request "finish anything about docs"

The output prints each swappable piece as it is chosen, then the generated program, then the answer — which is the same eight steps above, on one screen.
